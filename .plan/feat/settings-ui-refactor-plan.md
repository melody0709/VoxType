## 0. 结论先行

| # | 判断 |
| --- | --- |
| 1 | 这个决策的**唯一主轴是 IME**，不是渲染器、不是内存、不是语言。方案应按"是否接管文本输入"分成两族，其余维度都是次要的。 |
| 2 | **家族 A（不接管文本输入）**：布局引擎 + 表驱动声明 + 自绘 chrome。零 IME 风险、零新运行时、零新语言，三个痛点全解。**推荐为默认路线。** |
| 3 | **家族 B（接管文本输入）**：候选为 RmlUi / Slint / ImGui。家族 B 的入场券是"IME 先证明可用"，不是"界面更好看"。 |
| 4 | 家族 B 里，**RmlUi 是原文档漏掉的最优候选**：MIT、自有布局引擎（非浏览器内核）、**2024 年已实现原生 Win32 IME**、可复用项目现有 D2D/DWrite 渲染栈。 |
| 5 | **Slint 应从"首选"降级为"候选之一"**。它的中文输入存在**具体在案、上游阻塞的 open bug**，而非"未知风险"——"未知"可以先 spike，"上游阻塞"则是排期不可控。 |
| 6 | 一个**被原文档低估的关键成果**：保留原生 `EDIT` 控件**不等于**放弃观感。给 `EDIT` 做背景穿透 + 自绘外框，可以同时拿到"原生 IME"和"现代化外观"。这条把家族 A 的观感上限大幅抬高。 |
| 7 | 不建议先做技术栈 spike，**建议先做字段注册表**（第 8 节第 1 步）。它与 UI 技术栈完全解耦，收益最大、风险最低，且无论最终选哪族都是必经之路。 |

## 0.1 需求基线（用户确认，作为方案的范围锚）

用户对本轮重构的要求只有三条：

| # | 要求 | 由谁满足 |
| --- | --- | --- |
| **R1** | 未来**加行 / 删行要简单** | 布局引擎（组高由内容推导）+ 表驱动声明 |
| **R2** | 要有**"一定的"美观性**（不是极致） | 自绘 chrome（A4） |
| **R3** | **适合现代软件的要求** | 布局引擎（可拉伸 + 重排）+ 自绘 chrome |

**这三条恰好否掉了家族 B。** R2 的措辞是"一定的美观性"而非"最大美观性"——为了观感上限去接管文本输入、重新挣回 IME，**成本与收益不匹配**。家族 B 就此退出本轮范围（RmlUi 保留为长期备选，不做前置投入）。

**R3 是引入布局引擎的真正理由。** "适合现代软件"里最可感知的一条是**窗口可拉伸、内容跟随重排**。而当前设置窗口样式为 `WS_OVERLAPPED | WS_CAPTION | WS_SYSMENU | WS_MINIMIZEBOX | WS_CLIPCHILDREN`——**没有 `WS_THICKFRAME`，窗口根本拖不动**；且位置全部是编译期常量，即便加上厚边框内容也不会重排。这条是"是否真的现代化了"的分水岭。

### 由此确定的布局引擎选型：A2 Yoga

R1 与 R3 合并后，对布局的要求是"约束驱动的竖直栈式布局 + 输入框随宽度增长"。**建议选 Yoga（A2）**：文本测量（DWrite）无论哪条路都必须接，而 Yoga 提供的正是测量之外那层**约束传播与 flex 求解**——这是自研最容易写歪、最难调的部分。代价是一个 MIT 依赖 + 一行运行载荷清单。

### ⚠ 先澄清一个容易误读的点：A2 不是全部，A 路线是"三件套"

第 2 节把方案编号为 A1~A4，容易被读成"四选一"。**实际关系是**：

- **A1 与 A2 是二选一**（都只是"算矩形"的那一层，A1 自研、A2 用 Yoga）；
- **A3、A4 是叠加项**，与 A1/A2 正交，必须一起做。

| 你的要求 | 靠什么 | 性质 |
| --- | --- | --- |
| 加行 / 删行简单（R1） | **A3 字段表** | 纯 C++，零依赖 |
| 可拉伸 + 自动排布（R3） | **A2 Yoga** | **唯一新增依赖** |
| 好看一眼（R2） | **A4 自绘外观** | 复用已有 D2D / DWrite，零依赖 |

**所以"路线 A + Yoga"的完整表述是：A2（Yoga）+ A3（字段表）+ A4（自绘外观）。**
A2 只负责把矩形算出来，它既不会让"加一行"变简单，也不会让界面变好看——那两件分别由 A3 和 A4 负责。

**加行 / 删行的确切含义**（R1 的验收口径）：

> 加一行 = 字段表加一行表项；删一行 = 删掉该表项。
> 组高由内容推导，**不需要手改组高常量、不需要调整后续行索引、不需要改校验脚本**。

**若新增依赖不可接受的退路**：A1 自研游标（约 350 行：内容推导的竖直游标 + 一个 grow 列）即可满足 R1 与 R3 的**基本形态**，且零依赖。它唯一明显欠缺的是**窄宽度下提示文本的自动换行**。

> **选型的唯一负载问题：提示文本需不需要随窗口宽度自动重排？**
> 需要 → 选 Yoga（A2）。不需要 → A1 足够，且不必引入任何第三方代码。

## 1. 决策的真正主轴：IME 决定方案分家

原文档把 IME 列为"4 个 spike 之一"。**这个权重给低了。** IME 不是风险项，它是**分族判据**。

理由：VoxType 是**中文语音输入工具**，Settings 是**中文输入最密集的界面**。LLM Prompt、Qwen 敏感词表、热词表、各类 API Key 备注、provider 配置——大量字段要求用户用中文输入法**输入**，其中还有多行域。IME 一旦退化（候选窗不弹、预编辑丢字、上屏重复、失焦串位），是**用户当场就能感知的产品级故障**，且没有降级方案。

由此，方案自然分成两族：

```
                        ┌─ 家族 A：不接管文本输入
                        │   控件仍是原生 EDIT/COMBO
                        │   → IME 由 OS 免费提供，风险 = 0
   未来 Settings 重构 ──┤   → 要解决的是"矩形从哪来 + 声明在哪写 + 观感怎么提"
                        │
                        └─ 家族 B：接管文本输入
                            自绘文本框，自建 IME 集成
                            → 观感上限最高，但要重新挣回 IME
                            → 入场券 = IME 实测通过
```

**判据**：任何方案，如果既不能让原生 `EDIT` 继续存在、又没有**已实现并验证过的 Windows IME 集成**，直接出局——不论它多好看。

## 2. 方案全集

### 2.1 家族 A：不接管文本输入

| 方案 | 是什么 | 解决哪条痛点 | 代价 |
| --- | --- | --- | --- |
| **A1 顺序堆叠布局游标**（自研，约 300 行） | 布局游标随内容推进，组高由内容推导 | 加行难 / 易出错 | 无。零依赖 |
| **A2 Yoga 布局引擎** | Meta 的 flexbox 引擎，**只算矩形**，不渲染、不建事件循环、不接管控件 | 加行难 / 易出错 | MIT、零依赖、~600 KB；C++20 要求已满足 |
| **A3 表驱动声明** | 每页一张静态表，通用工厂据此建控件 + 定布局 + 做 Load/Save | 加行难 / 易出错 | 一次性重构控件创建路径 |
| **A4 自绘 chrome** | 用项目**已有**的 D2D/DWrite 画分组卡片、Tab 头、按钮 | 不好看 | 纯绘制工作，不碰控件、不碰 IME |

**A1/A2 二选一，A3、A4 与它们正交，可叠加。** A2 的定位是"恰好只做几何"，是本项目最贴合的形态：它不改动任何现有行为——原生 `EDIT` 及其完整 IME 行为、现有消息处理与命令分支、D2D/DWrite 渲染路径全部不动，**改的只有"矩形从哪里来"**。

**A1 vs A2 的选择口径**：如果团队希望"零第三方代码进仓库"（对分发产物可控性要求高），选 A1——300 行、可读、可测、无供应链面；如果希望拿成熟 flexbox 语义（`gap`、`grow`、`align`、换行、绝对定位）并省掉自研调试，选 A2。两者都不是不可逆选择，A1 → A2 的迁移成本低。

### 2.2 家族 B：接管文本输入

| 方案 | 许可 | 布局 | 文本/IME | 依赖面 | 适配度评述 |
| --- | --- | --- | --- | --- | --- |
| **B1 RmlUi** | **MIT** | 自有布局引擎（XHTML1/CSS2 + flexbox + media queries） | **原生 Win32 IME 已实现**（2024，PR #541；`TextInputMethodEditor_Win32` 在 platform 层，与渲染器无关） | 仅 FreeType + 标准库；**字体引擎可替换**——项目已有 DirectWrite，可自实现 `FontEngineInterface` 接上去 | **家族 B 里唯一"四项全绿"的选项**：声明式标记、真布局引擎、非浏览器内核、IME 已验证。原文档未收录 |
| **B2 Slint C++** | GPL / 商业 / 桌面免版税商用三选 | 自有声明式布局（`.slint` markup） | winit 后端**已有 IME 管线**（preedit / commit），但**中文输入存在在案 open bug** | 构建期需 cargo；运行期 Slint DLL | 声明式体验最好、`stock_new` 已有现成范本；但中文输入缺陷**上游阻塞、排期不可控**。详见 §3.3 |
| **B3 Dear ImGui** | MIT | 无（immediate mode，逐帧算） | **Win32 IME 成熟**（`HAS_WIN32_IME` / imm32 / `Platform_SetImeDataFn`） | 自带渲染后端（D3D/GL/VK），需替换渲染路径 | IME 与许可都很好，**但它不解决"不好看"**——官方 FAQ 明说它是为调试工具设计、可皮肤化程度有限。放在这里是为了完整性，不是推荐 |

### 2.3 已排除（沿用前篇结论）

C# / .NET / WPF / WinForms、Tauri、Electron、任何内嵌浏览器内核的方案、Qt / wxWidgets / Sciter。

## 3. 方案前提的关键修正

### 3.1 C++23：门槛消失，但不是优势

前篇把"C++17 → C++20"当作一项独立风险与收益来评估。**该议题已经消解**：标准已到 C++23，Yoga、RmlUi、Slint C++ 的门槛全部满足，没有任何方案因标准出局。

同时要明确：**标准版本不是这个问题的解药**。加一行布局困难、加一个配置项要动十处、界面不好看——这三条在 C++17/20/23 下**完全一样**。不要把"标准已升级"当作"UI 已被重构"。决定成本的是**信息组织方式**（布局是否可求值、字段是否表驱动），不是语言标准。

### 3.2 一个被低估的成果：原生 EDIT 也能现代化

原文档隐含一个假设：想要好看 ⇒ 必须自绘文本框 ⇒ 必须接管 IME。**这个假设不成立。**

Win32 原生 `EDIT` 可以被做成"看不见背景、只留文字"：把控件背景置为透明、去掉 `WS_EX_CLIENTEDGE`、在父窗口用 D2D 画出圆角输入框与外框，控件本身负责文字、光标、选区与**全部 IME 行为**。这是大量现代化 Win32 应用的标准做法。

结论：**家族 A 的观感上限被显著抬高**。分组卡片、圆角、留白、层级、暗色主题全部可达；唯一做不到的是"输入框内文字本身的自定义排版"（如富文本、行内高亮）——而这在 Settings 里恰好不需要。

### 3.3 Slint 的 IME 状态：是"在案缺陷"，不是"未知风险"

这决定了两件不同的事：

- **未知风险** → 可以 spike 一小时内验证 → 可接受。
- **在案缺陷 + 上游阻塞** → 能不能解决不由我们决定 → 排期不可控。

Slint 属于后者：Windows 平台有明确在案的中文输入显示缺陷，标记为 Windows 平台问题、且标注为需要上游修复，自 2024 年 8 月起保持开启。这不是"可能有问题"，而是"已知有问题，等上游"。

**因此 Slint 的评估姿态应当改变**：不是"先 spike 再定"，而是"在上游修复落地前不投入重构"。前篇 §6 把 Slint 列为路 A 首选的建议，**基于当时的信息权重，现在应当下调**。

### 3.4 Slint 许可：比前篇描述的要清楚

前篇说"许可证未定、法律悬空"。实际情况是 Slint 提供**面向桌面/移动/Web 的免版税商用许可**，不必购买 GPL 商业豁免即可用于闭源桌面分发（需按其条款履行义务）。

这减轻了法律不确定性，但**没有取消它**：项目自身仍需声明 LICENSE，且采用前应逐条核对该免版税许可的具体条件。这是**决策前置条件**，不是收尾工作。

### 3.5 规模口径

前篇引用的行数与控件数基于旧快照。方案设计不依赖精确数字，但可分页边界按"页"而非"行"来划：Settings 共 5 个页签，其中 Cloud ASR 页内含 7 个 provider 子页与嵌套条件显示，是复杂度最高的一页。

## 4. 推荐路线

```
默认路线（推荐）：家族 A
    A2/A1 布局引擎  ──→  A3 表驱动声明  ──→  A4 自绘 chrome  ──→  校验改为求值真实布局

备选路线（仅在明确想要 markup 时启用）：家族 B1 = RmlUi
    前置条件：① 一个"中文输入完整闭环"的实测通过  ② 项目 LICENSE 落定

不建议：家族 B2 = Slint，在上游中文输入缺陷修复前
不适合：家族 B3 = ImGui，它不解决"不好看"这条痛点
```

**推荐家族 A 的核心理由不是"保守"，而是收益/成本比**：三个痛点里，有两个（加行难、易出错）**与平台完全无关**，根因是"布局不可求值 + 声明散落"；家族 A 精准命中这两条。第三个痛点（不好看）按 §3.2 也能在家族 A 内解决到相当程度。而家族 B 换来的**增量**只是"markup 比 C++ 表更顺手"，代价却是接管文本输入、重新挣 IME。

**如果最终选家族 B，选 RmlUi 而不是 Slint**：同为声明式、同为自有引擎（非浏览器）、MIT 许可无附加义务、且 IME 是**已实现**而非**待修复**。

## 5. 目标形态

### 5.1 家族 A（默认路线）

```
SettingsSpec（编译期，纯数据）
  ├─ 字段表    { 成员指针, JSON key, 类型, 默认值, 控件种类, 标签, 所属页, 所属组, 可见性规则 }
  ├─ 页面表    { page id, 标题, 组列表 }
  └─ 分组表    { group id, 标题, 行列表 }

        │  同一张表驱动四件事
        ▼
SettingsLayout（运行时，可求值）
  └─ 布局引擎 → 每个控件的 DIP 矩形 → DPI 换算 → 物理像素矩形

        ▼
SettingsView（Win32）
  ├─ 控件工厂：按字段表创建原生 EDIT / COMBOBOX / CHECK / BUTTON
  ├─ 自绘 chrome：D2D/DWrite 画卡片、Tab 头、按钮、输入框外框
  └─ Load / Save：遍历同一张表，双向同步

        ▼
SettingsValidation（可求值校验）
  └─ 对**算出来的真实矩形**做重叠与溢出断言（任意 DPI × 任意窗口尺寸）
```

关键性质：**"一个配置项的持久化信息"和"它的 UI 与布局信息"在同一行声明上**。这正是"加一个配置项 = 表里加一行"和"插一行 UI = 什么都不用做"能同时成立的原因。

### 5.2 校验脚本的形态变化

现有校验脚本用正则解析源码文本、在若干硬编码 DPI 下复算数值断言——这是"没有可求值布局"逼出来的退路。

目标形态不是"移植"，而是**改变断言的证据类型**：脚本调用布局引擎求值布局树，在任意 DPI、任意窗口尺寸下拿到真实矩形，再检测重叠与溢出。具名事故场景（各分组触底/超宽、字段与 footer 重叠、Endpoint 溢出等）**原样保留为测试用例**，但断言对象从常量变成算出来的矩形。

由此从"用文本正则猜几何"升级为"对真实几何做断言"——从脆弱的源码契约升级为稳固的几何契约。**"控件重叠"这一整类 bug 从根上消失。**

## 5.3 可拉伸性（R3）的实现要件

**结论：能拉伸，而且这正是布局引擎最直接的收益。但它不是"改个窗口样式"就完事，需要下面五件事同时到位。**

先明确今天的状况：设置窗口没有 `WS_THICKFRAME`，**用户根本拖不动边框**；即便加上，位置是编译期常量，内容也不会重排。"能不能拉伸"因此是判断布局是否真变成"约束驱动"的最简试金石——**如果引入了 Yoga 却仍喂给它固定的 850×740，那只是假的可拉伸，观感与行为都不会变。**

### 必须同时做到的五件事

| # | 动作 | 要点 |
| --- | --- | --- |
| 1 | **加窗口样式** | 加 `WS_THICKFRAME`。是否同时给 `WS_MAXIMIZEBOX` 需单独决定（设置窗口通常不给最大化） |
| 2 | **根节点吃客户区尺寸** | 每次布局把**当前客户区尺寸**作为根节点的可用尺寸传入，不再传固定常量 |
| 3 | **`WM_SIZE` 触发重算** | 尺寸变化 → 重新求值布局树 → 对每个控件 `MoveWindow`。DPI 变化（`WM_DPICHANGED`）走同一条路径 |
| 4 | **最小尺寸约束** | 在 `WM_GETMINMAXINFO` 里设下限，否则窗口可被拖到布局无法成立（标签被挤没、输入框归零） |
| 5 | **竖直溢出容器** | 内容高于窗口时要有滚动容器（或一个足够大的最小高度）。**Yoga 只给几何，不给滚动**——这是设计项，不是自动获得的能力 |

### 三个必须提前知道的坑

- **下拉框高度不可自由设定**：原生 `COMBOBOX`（`CBS_DROPDOWNLIST`）**收起态高度由字体推导**，`MoveWindow` 改它无效；现有 `ComboH`（150）是**下拉列表展开高度**，不是布局高度。它会成为"布局说 32px、实际不是 32px"的第一个意外。
- **DIP ↔ 物理像素**：根节点尺寸必须用 DIP（物理尺寸 ÷ scale），`MoveWindow` 用物理像素。与项目现有 HUD 规则是同一条，不能混用。
- **焦点与 Tab 顺序**：控件位置改为动态计算后，`WS_TABSTOP` 的键盘遍历顺序不再由创建顺序自然保证，需显式维护或让创建顺序与布局顺序对齐。

### 验收口径（补充）

> 在 96 / 144 / 192 / 288 DPI 下，把窗口从最小尺寸拖到最大化尺寸，内容全程无重叠、无溢出、无裁切；输入框随宽度增长；提示文本按需换行。

这一条与 §6 的"加一行"标准互补：一个测结构，一个测响应性。

## 6. 验收标准（可测试定义，建议写入 AGENTS.md）

**加一行 UI 的改动范围必须收敛为**：

> 在某个分组的中间插入一行新配置项（标签 + 输入框 + 提示文本），改动范围仅限于
> **1 处表项声明 + 1 处 Load/Save 字段 + 1 处配置结构体字段**，
> 且 **0 处坐标常量改动、0 处行索引调整、0 处组高调整、0 处布局校验脚本改动**。

**这是判断重构是否成功的首要标准。** 它可测、可回归、与"界面好不好看"这种主观标准互补。

**布局正确性标准**：

> 任意 DPI（至少覆盖 96/144/192/288）× 任意窗口尺寸下，无控件重叠、无控件溢出容器、无触底裁切。
> 该断言由校验脚本对求值后的真实矩形执行，而非对源码文本。

## 7. 迁移顺序

分页渐进。**不要一次性重写整个 Settings。**

| 步 | 动作 | 为什么这个顺序 |
| --- | --- | --- |
| 1 | **字段注册表 / 快照契约** | 与 UI 技术栈**完全解耦**；先把"加配置项动十处"收敛成一处。收益最大、风险最低，且两族都需要 |
| 2 | **布局引擎**（A1 或 A2），先只接一页 | 布局是"加行难"的根因；单页试点可控 |
| 3 | **表驱动控件工厂** | 与第 2 步天然是同一张表，但建议分两步落地，便于定位回归 |
| 4 | **自绘 chrome** | 纯绘制，不动控件与消息路径，风险最低、观感收益最直接 |
| 5 | **校验脚本改为求值真实布局** | 前四步做完才有"真实几何"可断言 |
| 6 | **Cloud ASR 页** | 7 个 provider 子页 + 嵌套条件显示 + 活状态刷新，最复杂，放最后 |
| 7 | **热键捕获** | 与全局键盘钩子的协调是独立设计问题，不能事后补 |

**试点页选择**：优先选**纯文本域、无 provider 分支、无活状态**的页（如 LLM Prompt 页）。Cloud ASR 页最后。

**迁移期间保留原实现作为回退**，逐页替换，每页做一次高 DPI 目视检查。

**若走家族 B**：第 1 步不变；第 2/3/4 步被"接入 RmlUi + 写渲染接口"整体替代；第 6、7 步的难度**上升**（活状态刷新要过桥、热键捕获要处理焦点与 IME 抢占），必须提前设计。

## 8. 需要做的实测（已收敛到最少）

家族 A 的实测负担**远小于**前篇的 4 个 spike——因为它不碰文本输入，而前篇的 4 个 spike 里有 3 个是 Slint 专属的。

| # | 实测项 | 适用族 | 说明 |
| --- | --- | --- | --- |
| 1 | **中文输入完整闭环** | B | 真实输入法输入：候选窗位置、预编辑显示、上屏正确、失焦/切页不丢字。**家族 B 的入场券** |
| 2 | **RmlUi 渲染接口可行性** | B1 | 用 D2D 实现 `RenderInterface`、用 DWrite 实现字体接口，确认圆角/裁剪等所需特性可覆盖；不可覆盖时退到其自带 DX12 后端（接受第二套渲染栈） |
| 3 | **布局引擎接入成本** | A | 把现有某一页的表达改写成布局树，度量改造量——这是 A1/A2 选型与工期估算的直接输入 |
| 4 | **空闲内存不被污染** | B | 家族 A 无此项。家族 B 若进程内加载，需确认未打开 Settings 时不付内存代价 |

**关键：家族 A 没有阻塞性实测项。** 这是它最大的隐性优势——不存在"做完实验发现方案不可行"的悬崖。

## 9. 不要做的事

- **不要在 IME 未验证前采用任何接管文本输入的方案。** 这是本方案的第一红线。
- **不要在 Slint 上游中文输入缺陷修复前投入 Slint 重构。** 风险不在我们手上。
- **不要为了"统一风格"顺手重写控件与消息路径。** 自绘 chrome 只应改绘制，不应改行为。
- **不要一次性重写所有页。** 分页渐进，每页可回退。
- **不要用"标准已升到 C++23"作为"UI 已现代化"的依据。** 两者无关。
- **不要引入 WebView2 / Tauri / Electron / .NET / Qt。** 与内存基线冲突。
- **不要假设"想要好看就必须自绘文本框"。** 见 §3.2。
