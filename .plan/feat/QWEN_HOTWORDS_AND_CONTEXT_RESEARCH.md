# 通义千问 Qwen-Audio 热词管理与上下文增强深度调研与差距分析报告

本文档基于阿里通义实验室 / 阿里云百炼（Model Studio）官方最新技术规范，对 VoxType 当前的**热词管理（Vocabulary）**与**上下文增强（Context Enhancement）**实现进行全面审计与对比分析，识别核心差距并提出优化方案。

---

## 1. 核心调研背景与官方技术规范

根据百炼官方文档《提升识别准确率》及 DashScope Qwen-Audio 3.x 协议：

### 1.1 热词体系规范 (Hotwords / Vocabulary)
1. **两类形态**：
   - **预编译热词（`vocabulary_id`）**：在控制台或通过 API 预先创建的持久化词表 ID，每个账号最多 10 个，必须严格匹配 `target_model`。
   - **即时热词（`parameters.vocabulary`）**：在单次识别请求中直接随 JSON 发送的键值对 `{"word": weight}`，无需预先创建。
2. **权重机制**：
   - **常规热词（1 ~ 5）**：**官方推荐起始基准为 `4`**（1~2 为轻微偏好，3~4 为明显偏好，5 为强偏好）。
   - **超级热词（50）**：大幅提升专有名词召回率，**仅支持赋值为 `50`**。
   - **配额红线**：单个请求中超级热词（`weight=50`）**严格限制最多 50 个**，总热词数最多 2000 个。
   - **官方避坑警示**：权重过高会导致发音相近的日常词被错误纠偏为热词。
3. **词长规范**：
   - 含非 ASCII（中文等）：总字数不超过 15 个字符。
   - 纯 ASCII（英文等）：按空格切分不超过 7 个单词片段。

### 1.2 上下文增强规范 (Context Enhancement)
1. **多轮对话结构**：
   - WebSocket 流式：在 `run-task` 的 `payload.input.context` 传入。
   - HTTP 批量：在 `input.messages` 中置于音频消息之前传入。
   - 支持角色：`user`（前几轮识别结果或专有词表）与 `assistant`（大模型回复）。
2. **容量与限制**：
   - **最多保留最近 5 轮对话**（超出时早期消息自动忽略）。
   - **每轮文本长度上限 400 字符**（超出从末尾截断，不报错）。
3. **生效机理**：
   - **词表原词匹配机制**：上下文主要通过发音与关键词匹配生效，`text` 字段中必须包含待识别的原词本身（如“Kubernetes”、“Bulge Bracket”），纯语义背景对 ASR 纠正效果有限。
4. **动态刷新**：
   - 实时流式支持通过 `continue-task` 在推流过程中动态追加或替换上下文。

## 3. 核心差距与缺陷对比剖析

| 领域 | 官方标准设计 | VoxType 现状实现 | 影响与严重等级 |
| :--- | :--- | :--- | :--- |
| **热词默认权重** | 常规热词推荐起始值 **`4`**；超级热词 **`50`** 仅限少数关键专有名词（最多 50 个）。 | `VocabularyEntry` 默认权重为 `50`；文本行输入时默认赋值 `50`。 | 🔴 **严重失真**：所有未填权重的普通词全部变成超级热词，不仅导致严重的发音过度误纠偏，而且瞬间耗尽 50 个超级热词配额。 |
| **权重转换规则** | 1~5 为普通梯度，50 为超级热词。 | `WeightToQwen`: `if (weight >= 10) return 50;`。用户若按百分制写了 10~49，全部被拉高到 50。 | 🟠 **设计粗糙**：缺乏平滑梯度，10 以上全成超级热词。 |
| **超级热词截断排序** | 超出 50 个超级热词时，应当优先保留用户最关注的超高优先级词。 | `TranspileToQwenJson` **未进行权重排序**，直接按词表遍历顺序截断。前 50 个设为 50，第 51 个之后降为 5。 | 🔴 **明显缺陷**：若用户在词表末尾写了最重要的 50 权重词，会被降级为 5；若词表超 2000，末尾词直接被静默丢弃。 |
| **上下文形态** | 原生支持 **5 轮对话历史**（`role: "user"` / `role: "assistant"`），能持续利用前几轮语音输入的上下文。 | **仅抓取当前聚焦输入框的单次文本（单轮 `user`）**，完全没有多轮语音输入历史缓存。 | 🔴 **严重差距**：用户连续说多句话时，前一句话的识别结果无法增强下一句，输入法多轮连续性断裂。 |
| **输入框为空时的上下文** | 上下文可传入“领域术语或词表”作为替代补充。 | 若当前输入框为空、或 UIA 抓取超时/失败，Qwen context 直接置空为 `{}`。 | 🟠 **后备缺失**：在很多无法获取文本的窗口（终端、游戏、Canvas 编辑器、新聊天窗），上下文增强完全失效。 |
| **文本截取方向不一致** | 官方超 400 字符从末尾截断；对输入法而言，光标前的最新内容最重要。 | `input_context.h` 用 `TakeLastN` 取尾部，但在 `qwen_context.h` 与 `streaming.cpp` 又用 `TakeFirstN` 截断。 | 🟡 **潜在矛盾**：长文本在不同层首尾截取逻辑交织，可能误裁光标紧邻的关键词。 |
| **`continue-task` 刷新时机** | 用于长音频/会话中动态追加关键词。 | 仅在用户松开按键后、`finish-task` 发送前几毫秒刷新一次，且默认关闭。 | 🟡 **效用受限**：由于网络 RTT，在终帧前发送对实时推流的前半程出字毫无助益。 |

## 4. 优化改进建议与路线图 (Action Plan)

### 阶段一：热词管理精准化改造（高优先级，低风险）

1. **修正默认权重与映射逻辑**：
   - 将 `VocabularyEntry` 默认权重调整为推荐的普通权重基准（如 `4` 或换算为 100 分制下的合理值）。
   - 在 `WeightToQwen` 中明确区分：只有显式指定 `50`（或 100 满分）才映射为超级热词 `50`；其余按比例映射至 `1 ~ 5`。
2. **在 Transpile 前进行稳定权重降序排序**：
   - 在 `TranspileToQwenJson` 中引入类似 `BuildLlmVocabularySection` 的 `std::stable_sort`，保证权重最高的 50 个词优先获得超级热词配额，多余的高权词平滑降为 5，总词数超 2000 时丢弃最低权重项。
3. **UI 体验优化**：
   - 在 `tab_vocabulary.cpp` 的状态栏与提示语中明确提示：“建议普通热词权重设为 4，超级热词设为 50（单次最多 50 个）”。

### 阶段二：上下文增强全流程升级（中优先级，高收益）

1. **建立全局 ASR 识别历史环形缓冲区 (Recognition History)**：
   - 借鉴火山引擎中的 `g_volcRecognitionHistory` 机制，将其抽象为通用的 `AsrHistoryManager`。
   - 当用户连续进行语音输入时，自动记录最近 3 ~ 5 轮的识别结果。
2. **多轮 Context 智能构造 (Multi-turn Context Builder)**：
   - 构造 `input.context` 结构时：
     - 若当前输入框有前置文本，作为当前轮 context；
     - 同时将最近 1~3 轮的历史识别文本按 `user` 角色注入历史 context。
     - 若当前输入框为空（例如新打开输入框），自动以历史识别记录或核心热词列表填充 `context`，避免上下文完全为空。
3. **统一 400 字符截断规则**：
   - 确保从光标前优先保留最近的 400 字符（`TakeLastN`），并与官方末尾截断规则对齐。
